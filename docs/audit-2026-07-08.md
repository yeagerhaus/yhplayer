# Pre-UI-Revamp Logic/Functional Audit — 2026-07-08

Audit of hooks/stores, native playback engine, Plex/data layer, and app routes/UI logic, done ahead of a UI revamp. Scope was deliberately non-visual — everything here is business logic that will likely survive the revamp untouched, so it's worth clearing out first.

Status legend: `[ ]` todo, `[x]` done. Update as items are fixed.

---

## P0 — Fix before/independent of the revamp

- [ ] **Switching Plex servers/accounts doesn't reset the API client**
  `utils/plex-client.ts`. `clearInitialization()` exists but is never called from `plexAuthService.selectServer()` / `logout()` / `loginWithToken()` (`utils/plex-auth.ts`). Client keeps `baseURL`/`token` from the old server/account until app restart.
  Trigger: user with 2+ Plex servers switches server in Settings → Account, or logs into a different account, without restarting the app. All subsequent requests silently go to the wrong server.

- [ ] **Music playback position is effectively never persisted during active playback**
  `hooks/usePlaybackProgressStore.ts:15-22`. `setPosition` debounces the storage write (2s), but it's called every 0.5s from `PlaybackProgressUpdated` — so the timer keeps getting reset and only actually fires once updates *stop* (i.e. on pause). Kill the app mid-track (no pause first) → stale/zero resume position.

- [ ] **Partial library restore never heals into the full queue**
  `hooks/useAudioStore.ts:474,524-583` + `app/_layout.tsx:182-206`. On cold library cache, `restorePlaybackState` sets `currentSong` from a single-track fallback ("partial restore… full queue pending"). The healing check in `_layout.tsx` only re-runs restore `if (!currentSong)`, which is now non-null — so the full queue is never actually restored. Likely the root cause behind the "restoring playback bug" commits.

- [ ] **Queue reorder/removal doesn't invalidate an already-prepared next track (native engine)**
  `modules/yhwav-audio/ios/AudioEnginePlayer.swift` (`scheduleNext`), `YhwavAudioModule.swift` (`remove`, `move`). Neither calls `clearCrossfadeIdle()`. Removing/reordering an upcoming track can leave a stale track preloaded on the crossfade idle deck or gapless node — it plays audibly before a hard-cut self-correction a few seconds later.

- [ ] **Rapid skip-taps race — stale index used after being superseded**
  `modules/yhwav-audio/ios/YhwavAudioModule.swift:533-600` + `AudioEnginePlayer.swift:337-390`. `play()` silently no-ops on stale generation instead of throwing, so a superseded `skip()` call still emits `PlaybackActiveTrackChanged` with the wrong index and schedules the wrong "next" track. Self-heals ~0.5s later via `ensureNextTrackPrepared`, but a short-enough next track can finish before correction lands.

## P1 — Systemic pattern: missing staleness/cancellation guards

Same "old async response clobbers newer state" shape shows up independently in four places — worth a deliberate sweep rather than four one-off patches.

- [ ] **Podcast search has no stale-response guard** — `app/(tabs)/(podcasts)/search.tsx:31-56`. Debounce timer cancels correctly, but once the async search starts there's no request-id/cancelled flag; an older in-flight response can overwrite newer results.
- [ ] **Now-playing artwork/background color extraction races on rapid skips** — `hooks/useUltraBlurColors.ts:81-135` and `modules/yhwav-audio/ios/YhwavAudioModule.swift:1272-1291` (`NowPlayingManager`). Neither checks that the resolved song/URL still matches the *current* track before applying the result.
- [ ] **Podcast feed refresh vs. concurrent `addFeed` — last-write-wins overwrites new feed** — `hooks/usePodcastStore.ts:200-227` (`fetchAllFeeds`) reads feeds/episodes once, loops sequentially, writes back once at the end; a feed added mid-refresh (`addFeed`) gets silently overwritten and un-persisted.
- [ ] **Native search-index epoch guard is a no-op** — `hooks/useSearch.ts:57-63`. `indexEpoch` increments but is never read/compared; fire-and-forget native `buildSearchIndex` calls can resolve out of order with no correction.

## P2 — Moderate, real but lower urgency

**Playback / native audio**
- [ ] Duration fallback uses raw milliseconds instead of seconds when native duration is unknown (`YhwavAudioModule.swift:981-999`, contrast the correct `/1000` in `expectedDurationSeconds`) — progress bar/duration briefly ~1000x off until true duration arrives.
- [ ] Crossfade ramp duration isn't clamped to the outgoing track's remaining time (`AudioEnginePlayer.swift:309-317,918-944`) — short/late-started crossfades can leave the incoming track quietly under-volume for a stretch after the outgoing audio has already stopped, with UI/Now Playing not updating until the full ramp elapses.
- [ ] Forward-seek on a still-downloading/streaming track desyncs displayed position vs. actual audio (`StreamingAudioSource.swift:342-351`, `AudioEnginePlayer.swift:612-642`) — UI shows the seeked-to time but audio resumes from wherever the download had reached.
- [ ] `remove()` has no guard against removing the currently-playing track (`YhwavAudioModule.swift:494-504,1093`) — if triggered, playback dangles silently with no advance/`PlaybackQueueEnded` event (UI currently only exposes remove for upcoming songs, so likely unreachable today).
- [ ] `lib/playerAdapter.ts:96-103` `add()` — inserting at queue position 0 silently appends to the end instead (contradicts its own comment); latent since no current caller passes `index: 0`.
- [ ] PodcastPlayer has no audio-session interruption/route-change handling, unlike the music `AudioEnginePlayer` — phone calls / unplugging headphones won't pause or resume podcast playback correctly.
- [ ] `QueueList.tsx`/`useAudioStore.ts` derive "current index" via `queue.findIndex(s => s.id === currentSong.id)` — breaks if the same track id appears twice in the queue (duplicate add, or repeat-queue wraparound); native `getActiveTrackIndex()` would be immune but isn't used here.

**Stores / hooks**
- [ ] Manually skipping a track never scrobbles it or adds it to Recently Played — only natural end-of-track advance does (`useAudioStore.ts` scrobble call sites vs. `skipToNext`/`skipToPrevious`).
- [ ] `addToQueue`/`playNext`/`removeFromQueue` can race on concurrent invocation (`useAudioStore.ts:825-891`) — each reads `get().queue` synchronously before awaiting a native call, so overlapping calls can desync JS queue state from the native TrackPlayer queue; downstream index-based remove/reorder then acts on the wrong track.
- [ ] Download queue progress counters can go inconsistent after `cancelQueue` (`useMusicDownloadsStore.ts:190-322`) — in-flight workers from a cancelled batch still increment `queueCompleted` against a new batch's `queueTotal`.
- [ ] Scrobble queue can produce duplicate scrobbles if the app is killed mid-flush (`utils/scrobble-queue.ts:42-60`) — persists once per batch, not per item.
- [ ] `usePlaylistEditor.save()` has no rollback/resync on partial failure (`usePlaylistEditor.ts:35-85`) — a mid-loop error leaves `editedTracks`/`originalRef` out of sync with what actually landed server-side.

**Data layer**
- [ ] Whole-library/section deletions on the server never propagate locally — both cache reload and throttled refresh gate store updates behind `length > 0` (`utils/cache.ts:192-197`, `utils/library-refresh.ts:23-27`), so an emptied playlist/section keeps showing stale local data indefinitely.
- [ ] "Recommended server" in discovery is chosen by list order, not verified reachability across servers (`utils/plex-discovery.ts:172-179,306-313`) — can nominate an offline server when a later one in the list is actually reachable.
- [ ] Timer leak on every Plex API request — `createTimeoutController` (`utils/plex-client.ts:256-261`) never clears its `setTimeout` on success, unlike the correctly-written equivalents elsewhere in the same file.
- [ ] `buildTrackURL` fast path blindly appends `?...` to the path (`utils/plex-client.ts:212-220`) instead of using `URL`/`searchParams` like the general-purpose `buildURL()` — would double up `?` and break the URL if a Plex-supplied path ever already has a query string.
- [ ] Unstable synthetic episode IDs (`utils/podcast-rss.ts:93`, falls back to array index when a feed item has no guid/link) shift when new episodes are prepended — causes repeat notifications for the affected feeds.
- [ ] Background podcast-check processes feeds sequentially and only persists the "seen" cache once at the end (`utils/background-fetch-task.ts:23-73`) — if the OS kills the task partway through (tight background budget), already-notified episodes get re-notified next run.
- [ ] Scrobble queue has no cap/TTL/de-dupe (`utils/scrobble-queue.ts:14,70-76`) — grows unbounded during extended offline listening.

**App routes / UI logic**
- [ ] `SongItem`'s "Go to Album/Artist" context menu does `router.back()` then `setTimeout(() => router.push(...), 100)` — corrupts back-stack history when used from a non-modal screen (Album/Playlist detail), unlike `SearchSongItem`/`PodcastEpisodeItem` which just push directly.
- [ ] New/artwork-less playlists silently vanish from the Playlists list and Home's "Recent Playlists" — both filter on `artworkUrl != null` (`app/(tabs)/(library)/(playlists)/index.tsx:18-34`, `app/(tabs)/(library)/index.tsx:43`), which Plex leaves `undefined` until it generates a thumb for a brand-new playlist. `hasNoPlaylists` empty-state also doesn't account for this, so the screen just looks blank.
- [ ] `HeaderBackButton`/`app/music/[id].tsx` fall back to `router.replace('/(tabs)/home')` — that route doesn't exist anywhere in the app.
- [ ] `React.memo` comparators on `SongItem`/`LargeSongItem`/`PodcastEpisodeItem` only check `queue?.length`, not contents/identity — a same-length reordered/filtered queue blocks re-render, leaving `playSong`/`handlePlay` closures over a stale queue.
- [ ] `isSearching` (raw query) vs. `searchResults` (debounced query) mismatch for ~300ms after each keystroke — `hooks/useSearch.ts` / `app/(tabs)/search/index.tsx` — can transiently show "no results for X" using results computed for the previous query.

## P3 — Dead code / no-ops (harmless today, but will look like real behavior to whoever touches these screens next)

- [ ] `usePlaylists().isLoading` (`hooks/usePlaylists.ts:9`) is `useState(false)` and never set `true` — the loading branch in the playlists screen is unreachable.
- [ ] Tab "reset to root when re-tapped while nested" logic in `app/(tabs)/(library)/_layout.tsx` and `app/(tabs)/(settings)/_layout.tsx` compares `usePathname()` against strings containing route-group parens (e.g. `'/(tabs)/(library)'`) — `expo-router` strips group segments from pathnames, so this condition can never be true; the feature has never actually worked.

Not a bug, just worth knowing if you revisit download quality settings.
